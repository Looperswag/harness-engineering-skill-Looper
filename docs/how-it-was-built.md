# 我和 Claude 一起搞了一套方法论:让 AI 不再反复犯同一个错

*「碎碎念:最近和 Claude 一起共创了一套叫 harness-engineering 的 skill。起因是我做副业项目时反复踩同一类坑,后来读了几篇外部内容,才发现这是一个有名字、被系统研究过的领域。这篇文章把这个过程整理一下——为什么会有这个 idea、skill 里每个文件背后的设计哲学,以及它在工程实践上意味着什么。文末有 GitHub 链接,可以直接拿走用。」*

读完这篇文章你会得到什么:

- **PART 1** — 这个 idea 是怎么从几个外部输入里慢慢长出来的
- **PART 2** — 这份 skill 长什么样,每个文件背后的设计哲学
- **PART 3** — 三个真实场景,说明它在工程实践上的工程意义
- **PART 4** — 一个比 skill 本身更大的判断,以及彩蛋

一句话先抛我看完整个过程的最大体感:

> **2026 年做 AI 协作的真正分水岭,不是你用什么模型,而是你给模型搭了什么 harness。**

下面进入正题。

---

## PART 1 — 这个 idea 是怎么长出来的

### 一个真实的痛点起点

最近我在做一个副业项目,vibe coding 路线——我做 PRD 和审计,Claude Code 写代码。两万多行代码堆起来之后,我发现自己反复在同一类坑里打转:之前修过的问题在新代码里又冒出来,项目级的约定每次新会话都得重新讲一遍。

这些事我一开始都归因到"模型不够聪明",但越踩越多,我开始怀疑:**问题真的在模型吗,还是在我?**

下面这四片拼图,是我接下来一个月陆续读到的内容。看起来主题不同,但读完之后我发现, **它们都在讲同一件事的不同切面** ——而我项目踩的那些坑,本质上是同一个根因。

### 第一片拼图 — 肖涵的 Agent Memory 演讲

肖涵作为 Jina AI 创始人(后来被 Elastic 收购),在 4 月的 Elastic 中国大会上做了一个关于 Agent Memory 的演讲,核心论点是「2026 年做搜索就是做 Agent Memory」。

我读完印象最深的不是技术细节,而是他用一个 911 case 做的归因——他让 Agent 帮他找之前做过的"911 图表"(他指的是保时捷 911),但 Agent 把"911"理解成了恐怖袭击,完全找不到。整条记忆链路都是好的,只是 Query 的第一个字写错了,整个检索就废了。

他的判断是: **Agent 系统的失败,80% 发生在它正式开始检索之前——发生在 Query 改写这一公里**。

这个观察让我意识到:**我项目里那些坑也有相同的结构——失败发生在"上下文进入模型"之前,不是"模型不够聪明"**。

### 第二片拼图 — EvoMap × 清华的 Gene 论文

这篇论文有个让我后背一凉的发现:**完整的 Skill 文档在强模型上反而比无指导基线还差**——因为 Skill 文档里大量"为人类可读性服务"的内容,稀释了真正影响模型决策的控制信号。

更让我有共鸣的是它的另一个结论:**失败经验最佳的沉淀形态,不是 trajectory log,不是 reflection summary,而是蒸馏过的 AVOID 短句**。

这给了我具体的灵感:**我那些反复出现的"打地鼠"问题,需要的不是更详细的解释,而是一句一句简洁的 AVOID**。形态比内容更重要。

### 第三片拼图 — 李宏毅老师的 Harness Engineering 一讲

这一讲是我看完之后真正"啊就是这个"的那一刻。他把整个问题命了名——叫 **Harness Engineering**。

他的论点是:Prompt → Context → Harness 是一条演进路径,人类不仅要写 prompt,还要通过 harness 去控制模型的认知框架、能力边界和行为流程。具体抓手有三层:**AGENTS.md 这种自然语言规则、工具权限和能力控制、planner/generator/evaluator 这类工作流**。

这一讲帮我把模糊的直觉变成了清晰的概念分层。前两片拼图告诉我"问题真实存在""解药的形态长什么样",这一片告诉我"这件事有名字、有抓手、有研究框架"。

### 第四片拼图 — DeepMind 的 AutoHarness 论文

这篇是 4 月底刚发的,算 Harness Engineering 思想的极端化推进——既然 harness 这么重要,**让模型自己分析失败案例自己写 harness 代码**行不行?

结论是行,而且效果惊人:小模型加 AutoHarness,在游戏 benchmark 上打败了 GPT-5 系列。这个工作给了 Harness Engineering 一个"自动化路径",让我看到这个方向的天花板可能比我想象的高得多。

### 拼图合体

四片拼图拼起来,完整的图景浮现了:

```
肖涵:    问题发生在模型推理前的"第一公里" 
EvoMap:  解药的形态是结构化的、紧凑的、AVOID 短句为主
李宏毅:  这件事有名字、叫 Harness Engineering、有三层抓手
DeepMind: 这条路天花板很高、可以自动化
```

我项目里踩的那些坑,本质上是**没有 harness 系统设计**——既没有项目级的 AGENTS.md 锚定上下文,也没有把反复出现的问题蒸馏成 AVOID,更没有任何形式的工作流约束。

读完这四份内容,我做了一个决定: **把这套理解沉淀成一份 skill,以后每次开新项目都能复用** 。这就是接下来 PART 2 要讲的那份 skill。

## PART 2 — 这份 skill 长什么样,每个文件的设计哲学

我和 Claude 一起设计了一份 Anthropic Skills 标准的 skill,叫 `harness-engineering`。结构是这样的:

```
harness-engineering/
├── README.md               # 项目门面 + 快速开始
├── SKILL.md                # 主入口,三层框架概述
├── AGENTS_template.md      # 可填空的 AGENTS.md 模板
├── tool-permissions.md     # 工具权限设计
├── workflow-patterns.md    # 工作流模式详解
└── checklist.md            # 30 分钟启动方案
```

我不想把这一节写成"目录复述"——你直接读 README 比看我转述强。我想讲的是**每个文件背后的设计哲学**——为什么是这些文件、为什么是这种形态、为什么不是别的样子。

### `SKILL.md` — 一份"知道什么时候不要调用自己"的 skill

主入口文件最关键的不是"讲了什么",而是 **"什么时候应该调用我、什么时候不应该"** 。这是我和 Claude 反复打磨的一节。

容易写错的版本是:"调用本 skill 的场景:任何需要 AI 协作的项目"——这种宽泛触发条件会让 skill 在不该激活的时候激活,污染对话。

正确的版本是非常严格的边界:

> **不应该调用的场景:**
> - 单次性 prompt 调优(那是 prompt engineering)
> - 纯模型选型问题(更强的模型 ≠ 更好的 harness)
> - 跟编码无关的 Agent 系统

**一个好的 skill,首先要知道什么时候不要调用自己。** 这个原则我借鉴自 EvoMap 论文——他们的 Gene 设计里有个 `signals_match` 字段,用正则和关键词精确锚定触发条件。你要为你的 skill 划清楚边界,不然它会变成一个"什么都能用但什么都用得不好"的工具。

### `AGENTS_template.md` — 一份"自带文档反审"机制的模板

这是整套 skill 里最实用的一个文件——一个可以直接复制填空的 AGENTS.md 模板。但我和 Claude 在做的时候加了一层"反审机制"——模板末尾有一个 checklist,强制你在写完之后做一次反向 review:

```
□ 全文是否删除了所有"为人类可读性服务"的内容?
   - "项目愿景""我们的使命""设计哲学""感谢贡献者" → 删
□ 全文是否避免了抽象原则?
   - "写干净的代码""保持高质量" → 改成可验证的具体规则
```

这一层反审的灵感来自第二片拼图——EvoMap 论文证明了 Skill 文档里"为人类可读性服务"的内容在强模型上是负贡献。但人在写文档时会本能地追求完整性,会忍不住写"项目愿景""设计哲学"这种东西——**这是给同事看的,不是给 AI 看的**。

反审 checklist 是一种自我对抗机制:**强制你写完之后狠心删掉那些冗余**。如果你写过 README,你会发现这种"自己写完又自己删"的克制其实非常难——所以工具层面要替你做这件事。

### `tool-permissions.md` — "用减法定义 Agent"

这个文件讲工具权限设计,核心思想是**"用减法定义 Agent"**——不要列举它能做什么,要圈定它不能做什么。

文件里那个"五层级权限分类"——读取 / 执行 / 变更 / 外部影响 / 不可逆破坏——其实直接对应不同层次的失败成本。Level 5"不可逆破坏"那一栏写得最严:**这一类操作不应该让 Agent 直接执行,必须经过人工 approval 这一道**。这不是技术规范,是责任归属——**一旦 Agent 自动执行了不可逆操作并出了事,责任谁来承担?**

这一节的设计哲学是:**Agent 的能力边界,不能依赖模型自觉,必须靠工具层面强制**。

为什么?因为自然语言约束的脆弱性是真实的——你在 prompt 里写"不要 force push 到 main",模型大概率会遵守,但在某些边缘情况下(被对抗性 prompt 引导、上下文被截断、误解了指令)就可能违反。**对于不可逆操作,你不能接受"大概率"——必须是"100% 不可能"**。这只能靠工具的 deny list 而不是 prompt 的软约束实现。

### `workflow-patterns.md` — 一份"反过度设计"的文档

这个文件讲 Planner-Generator-Evaluator 工作流。但我和 Claude 写这份文档时,反复克制自己——**整个文件三分之一的篇幅在劝你不要用工作流**。

第一节标题就是"你真的需要分角色工作流吗?"——三个判断问题,每一个都在试图说服你"也许不需要"。这种反向引导是有意为之的:**Planner-Generator-Evaluator 是当下 AI 协作领域过度设计最严重的一个点**。

工程师本能是"看到一个范式就想用",而 harness engineering 的精神恰恰是"用最少的结构解决最多的问题"。**所以这份文档的第一价值不是"教你怎么搭工作流",而是"帮你判断你不需要工作流"**。

这跟主流 prompt engineering 的引导方向相反——主流引导你"加更多结构",我们引导你"先证明你需要结构,再加"。

### `checklist.md` — 30 分钟启动方案

最后这个文件本来叫"实施 checklist",我和 Claude 都觉得名字太正式。后来加了一个"30 分钟启动方案"小节:

> 如果你只有半小时,想快速给一个新项目搭起最小可用的 harness:
> - 前 10 分钟做诊断
> - 中间 15 分钟写 AGENTS.md
> - 最后 5 分钟跑验证

为什么单独抽出来?因为大多数人读完一份方法论之后,第一反应是"听起来很有道理"——然后就没下文了。**真正的转化发生在"30 分钟内能产生第一个产物"的场景**。

这一节的设计哲学:**好的方法论文档,不仅要讲对的事,还要降低应用它的启动成本**。

### `README.md` — 为不同读者画像分流

最后是仓库门面 README。这个文件做的事比看起来重要——它在第一屏就明确**这个 skill 不是给所有人的**,而是给四类特定读者:个人开发者 / 小团队 / Agent 系统设计者 / AI 协作研究者。每一类都给了不同的启动路径。

为什么要分流?因为 GitHub README 的常见反模式是"对所有人讲同一个故事",结果就是对所有人都没讲透。**承认你的内容只服务于特定人群,反而是对读者的尊重——不是你的目标读者的人,直接就走;是的人能立刻定位到自己该看哪部分**。

## PART 3 — 三个真实场景,说明这套 skill 的工程意义

讲了一大堆设计哲学,这一节落到具体——三个场景,每个场景对应一类用户。

### 场景一:个人开发者做副业项目

这是最朴素的用法。你一个人做一个小项目,大部分代码用 Claude Code / Cursor 写。

**之前的状态:** 每次开新会话,你都得先解释一遍项目背景、技术栈、约定。讲三五次之后你不耐烦,Claude 也忘得快。结果就是反复犯同一类错误,你修一遍它再犯一遍。

**用了 skill 之后:** 第一次开项目花 30 分钟写 AGENTS.md,把项目背景、技术栈、约定、AVOID 列表一次写好。之后的每一次会话,Claude 都能"一进入项目就懂"。每次发现新坑,你只在 AVOID 列表里加一句"AVOID xxx",下次就不会再犯。

我自己的记账项目用了之后最直接的感受是: **Claude 的"项目记忆"突然有了** ——它知道我们项目里 Divider 是反模式,知道功能必须真的在 Release 下工作,知道 token 体系只能用主体系不能用旁支。这些 know-how 不再依赖我每次手动提醒,而是嵌在了项目环境里。

### 场景二:小团队协作(假设你有 3-5 人一起用 AI 工具)

这种场景下问题会被放大——一个人小心,五个人不一定都小心;一个人记得项目约定,新人未必记得。

**关键差异:个人项目可以依赖"软约束"(写在 AGENTS.md 里靠模型自觉),团队项目必须有"硬约束"(工具层面强制)**。

举个例子:你团队某个新人对 Claude Code 不熟,他在 prompt 里说"帮我修一下这个 bug",Claude 决定改 prod 配置去 fix。如果你只有 AGENTS.md 而没有工具权限,Claude 会照做——AGENTS.md 是给 Claude 看的,不是给系统看的。但如果你把"`.env*` 文件禁止编辑""`production` 路径下文件需要 approval"这些写进 Claude Code 的 settings.json,系统会直接拒绝这次操作。

**软约束防 95% 的情况,硬约束守住最后 5% 的不可逆灾难**。团队场景下两层都不能省。

### 场景三:严肃 Agent 系统(对外提供服务)

这种场景最复杂,也是 workflow-patterns.md 真正能派上用场的地方。

如果你做的不是辅助编码而是一个对外提供服务的 Agent 系统(比如客服 Agent、数据分析 Agent、研究助理),你会面临两个新问题:

第一,**任务往往不是单步的**——用户提一个需求,Agent 需要理解、规划、执行、验证多步,中间还可能要根据情况调整路径。这时候单角色 Agent 经常表现"急于动手没想清楚",这是双角色 Planner+Generator 工作流真正能改善的场景。

第二,**用户的输入是不可控的**——他会用各种各样你想不到的方式表达同一个需求。这时候 AGENTS.md 里的 Domain Vocabulary 一节会变得关键——它告诉模型"我们这个领域里 X 是什么意思",避免模型用通用语义去理解专业术语。

如果你在做这类项目,我建议三层都做:Layer 1 + Layer 2 + Layer 3 一个都不能少。

## PART 4 — 一个比 skill 本身更大的判断

回到最开始那句话:

> **2026 年做 AI 协作的真正分水岭,不是你用什么模型,而是你给模型搭了什么 harness。**

这句话不只是这套 skill 的总结,更是我做完这件事后对整个 AI 协作领域的一个判断。

过去两年大家关注模型本身——GPT-4 vs GPT-5、Claude 3 vs Claude 4、参数量从 70B 到 235B。这些当然重要,但**模型能力的提升,边际收益是递减的**。一个用 GPT-3 写的高质量 prompt + 完整 harness,能轻松打败一个用 Claude Opus 但只有空 prompt 的协作。

而 harness 这件事,完全在你的控制范围内。它不需要你买更贵的模型订阅,不需要你等 Anthropic 或 OpenAI 发新版本——你只需要花几个小时,把项目级的约束、领域词汇、AVOID 列表、工作流写成 AGENTS.md。这个回报是立竿见影的,而且会随着你使用 AI 协作的深度持续累积。

**模型是别人的,harness 是你的。** 这是这套方法论最朴素也最重要的判断。

### 彩蛋:这份 skill 是和 Claude 共创的

最后讲一个元层叙事。

这份 skill 不是我一个人写的——它是我和 Claude 一起,通过几小时的对话共创出来的。我提出"想把这套理解沉淀成 skill"的需求,Claude 帮我设计文件结构;我说"AGENTS_template.md 应该有反审 checklist",Claude 帮我把这个想法落实到具体的字段里;我说"这部分太冗长",Claude 把它精简到三分之一。

整个共创过程本身就是 harness engineering 的应用——我作为人类提供了方向、价值判断、领域经验;Claude 提供了执行力、结构感、细节填充。我们用了我自己写的 CLAUDE.md(里面包含"修改超过 3 个文件先停下来拆分子任务""写完代码主动列出潜在风险"等约束),让这次协作非常高效。

**这件事本身就是这套 skill 想表达的核心思想——好的 harness 不会取代任何一方,它让人和 AI 都能发挥各自最擅长的部分**。
